## M1 — Profiles, uploads, validation

- **JWT auth added**, even though `claude.md`'s milestone breakdown doesn't call it out as an M1 task explicitly — the API contract (§6) states "JWT auth except `/internal/*`" for every route, and M1 is where the first user-facing endpoints beyond `/healthz` exist. Minimal single-user implementation: `POST /api/v1/auth/login` checks the email against `FOUNDER_EMAIL`, get-or-creates that one `User` row, issues a 30-day JWT. No refresh flow — not needed for a single-user local tool.
- **Split S3 endpoint config** (`S3_ENDPOINT` vs `S3_PUBLIC_ENDPOINT`): the API container reaches MinIO via the docker network hostname (`minio:9000`), but a presigned URL's signature is bound to the host it's signed for — so a URL signed against `minio:9000` would be unusable by a browser/host machine, which has no DNS entry for `minio`. `S3_PUBLIC_ENDPOINT` (only set in `docker-compose.yml`, defaults to `S3_ENDPOINT` otherwise) is used exclusively for presigning; the internal endpoint handles all server-side object operations. In production (Cloudflare R2) both will be the same single public URL, so this only matters for local dev.
- **Face/hand detection uses MediaPipe's legacy `solutions` API** (`face_detection`, `hands`), not the newer Tasks API. The Solutions API bundles its models inside the pip package, so no runtime model download is needed — simpler and more reliable in a Docker build with no guaranteed network access at container-run time.
- **Frame extraction's "frontal-ness" score is a simplified heuristic** (eye/nose-tip horizontal symmetry from MediaPipe's 6 face-detection keypoints), not full head-pose estimation. `claude.md`'s M1 acceptance criteria only requires golden fixtures to pass and a bad photo to be clearly rejected — not a validated head-pose model. Revisit if the auto-selected primary reference photo turns out to pick poor angles in practice.
- **Photo sharpness threshold is a fixed absolute cutoff (100, variance of Laplacian)**, per `claude.md`'s explicit "start ~100" guidance — not a bottom-decile relative comparison, since M1 validates each upload independently rather than against a batch.
- **Voice sample validation is a standalone endpoint check** (duration ≥30s + `ffmpeg volumedetect` loudness check on an uploaded `voice_sample` asset). The "extract audio from the reference video as a fallback when no separate voice sample exists" behavior described in `claude.md` M1 is actually exercised at voice-clone time — deferred to M2 where it belongs.
- **Verified end-to-end locally** (`docker compose up --build`): login → profile create → presigned upload → PUT direct to MinIO → asset validation, using a deliberately bad synthetic photo (200x200, blank, no face). All three expected rejections fired with clear messages: low resolution, blur, no face detected.
- **Photo sharpness is scored on the detected face region, not the whole frame** — found via real fixture testing: all 3 of the Director's genuinely-in-focus real photos were rejected as "blurry" because a large plain white background behind a zoomed-in portrait drags the frame-wide Laplacian variance down regardless of whether the face itself is sharp (whole-frame scores were 62-83; the same photos' face-region scores were 90-141). Whole-frame scoring is the wrong signal for "is the person in focus" on exactly the zoomed-in shots `claude.md` asks for. Fixed by detecting the face first, then computing sharpness only on that crop; falls back to whole-frame scoring when face count isn't exactly 1 (already fails for other reasons in that case). Frame extraction's candidate scoring got the same fix, for consistency.
- **Video frame rotation correction was a critical, non-obvious bug** — the Director's real reference video (iPhone, portrait, HEVC/MOV) is stored as 3840×2160 raw sensor frames with a `rotation: 90` flag in its Display Matrix side-data. `cv2.VideoCapture` decodes the raw (sideways) frames and silently ignores that flag. Every face/hand detection in this milestone was running on 90°-rotated frames — `single_face_ratio` measured **7.7%** on the real video despite the Director's face being in frame the whole time; `hands_ratio` (88.5%) looked fine only because MediaPipe's hand detector tolerates rotation far better than its face detector does. Fixed by reading the rotation from `ffprobe`'s `side_data_list` (falling back to the legacy `tags.rotate` field for older files) and rotating each decoded frame back to upright — via `cv2.rotate()` — before any detection or scoring runs, in both `media_validation.py` and `frame_extraction.py`. **Rotation direction (90 → `ROTATE_90_COUNTERCLOCKWISE`) was verified empirically**, not assumed: extracted a raw frame, rendered both rotation directions, visually confirmed which one was upright before writing the fix. After the fix, `single_face_ratio` on the same real video went to **100%**. This is very likely to recur with every phone-recorded portrait video, so it's not a one-off — any future validator/extractor touching raw video frames must account for rotation metadata.
- **Golden fixture media lives in `assets/test/` locally but is *not* committed to git** — deviates from `claude.md`'s literal repo layout, which shows `assets/test/` as part of the tracked repo. Two reasons: (1) the real reference video is ~190MB, and GitHub hard-rejects any file over 100MB without Git LFS — committing it as-is would simply fail; (2) it's the Director's actual face/voice, and there's no need to carry personal media in git history indefinitely just to have fixtures available. Only the small text fixtures (`script.txt`, `emotion_brief.txt`) are tracked; photos/video/audio are `.gitignore`d and stay local-only. If Git LFS becomes worth adopting later (e.g., a second machine needs the same fixtures), revisit this.
- **Golden fixtures verified for real** (2026-08-19), closing M1's acceptance criteria in full: 3 of 5 real candidate photos passed (2316×3088, resolution/face/zoom all clean — the other 2 correctly failed sharpness, and visually are in fact slightly softer); the real 51.5s/4K/24fps reference video passed after the rotation fix, with `single_face_ratio=1.0` and `hands_ratio=0.885`; 12 frames were extracted and the auto-selected primary reference frame was visually inspected — upright, sharp, natural; the real 54.6s voice sample passed (mean volume -16.3dB). Consent confirmed via the live API. **Final checklist on the test profile: `ready=true`.** M1 is fully closed.

- **Qwen-Image-Edit-2511 pipeline verified against the live HF model card** (2026-08-19):
  - Diffusers pipeline class: `QwenImageEditPlusPipeline`. Requires diffusers installed from git (`pip install git+https://github.com/huggingface/diffusers`) — the PyPI release doesn't have this class yet.
  - Exact generation kwargs from the card's quickstart: `torch_dtype=torch.bfloat16`, `true_cfg_scale=4.0`, `negative_prompt=" "`, `num_inference_steps=40`, `guidance_scale=1.0`, `num_images_per_prompt=1`, `generator=torch.manual_seed(N)`. `look_generation.py` uses these verbatim rather than guessing sane-looking defaults.
  - No Lightning/distilled fast variant exists yet specifically for 2511 (only for 2509 and the base `Qwen-Image` model, per `lightx2v/Qwen-Image-Lightning`'s file listing) — M3 runs the full 40-step pipeline, not a fast 4–8 step one. `claude.md`'s Lightning-variant note applies to 2509, not 2511.
  - Both the 2509 and 2511 model cards note "optimal performance ... with 1 to 3 input images" — `look_generation.py` caps total input images (reference + garment + extra photos) at 3 even though the API can hand it up to 4.

- **Job queue built as a generic table, not domain-aware** — the worker only ever talks to `/internal/jobs/*` and knows nothing about `Look`/`VideoRequest` rows. When a job completes or permanently fails, the control plane (`routes/internal.py`'s `_apply_domain_side_effects`) looks up the right domain row from `job.payload` and updates it (e.g. `look.candidate_keys`, `look.status`). Keeps the worker protocol identical across job types (`look_generation` now, `video_generation`/`upscale` at M5) instead of adding domain-specific worker endpoints.
- **Added `jobs.progress` column** (migration `0002`) — `claude.md` §5's literal jobs schema omits it, but §6's worker protocol (`PATCH .../jobs/{id} {progress}`) and `GET /jobs/{id}` (UI polling, 0–100) both require one. Storing progress inside `result` would conflate final output with interim state.
- **Job leasing uses `SELECT ... FOR UPDATE SKIP LOCKED`** with a reclaim path: `lease_next` picks up either a `queued` job or a `leased`/`running` job whose `lease_expires_at` has passed (a worker that crashed or was killed mid-job never checks back in). Both paths count against the same `attempts` budget (max 2, per §5) — exceeding it marks the job `failed` outright during the lease attempt rather than leasing it a third time. Verified live: two explicit `/fail` calls on the same job went `queued` (attempts=1) then `failed` (attempts=2), and the linked `Look.status` flipped to `"failed"` on the second one.
- **Worker fetches/uploads via presigned HTTPS URLs, not direct S3/MinIO credentials.** The control plane presigns GET URLs for input images (`reference_image_url`, `extra_reference_image_urls`, `garment_image_url`) when it enqueues the job, and the worker gets presigned PUT URLs for outputs via `POST /internal/uploads/presign`. Keeps the worker's only credential the `WORKER_TOKEN`, matching the architecture's "worker authenticates with a worker token" principle — no S3 secret ever leaves the control plane. Added `presign_get` (`storage.py`, 1hr expiry — longer than the 15min PUT window, since a queued job might sit a while before a pod is up) and a generic `build_key(prefix, filename)` helper alongside the existing profile-scoped `build_object_key`.
- **Added `garment` as an uploadable `MediaAsset` kind** (`validate_garment` in `media_validation.py`) — `claude.md`'s M3 description mentions an optional "wear this shirt" garment image and `looks.garment_asset_id` references `media_assets`, but the original M1 upload validation only recognized `photo`/`reference_video`/`voice_sample`. Garment validation skips face/sharpness checks entirely (decodable image + ≥512px short side only) since a garment photo isn't expected to contain a face.
- **Local dev API/MinIO reached from the RunPod pod via reverse SSH tunnel** (`ssh -R 8000:localhost:8000 -R 9000:localhost:9000`), not a public tunnel (ngrok etc.) or a real deployment — `claude.md`'s `API_BASE_URL=https://api.yourdomain.com` assumes a production deployment that doesn't exist yet. The pod's worker uses `API_BASE_URL=http://localhost:8000`; presigned S3 URLs are signed against `S3_PUBLIC_ENDPOINT=http://localhost:9000`, which resolves on the pod through the same tunnel. Kept the local dev secrets (`.env`, real API keys) off the public internet entirely. Revisit only if remote/production deployment becomes real.
- **Two real bugs found and fixed via the live M3 pod run** (2026-08-19), neither of which a dry-run/mock would have caught:
  1. **`pip install torch` silently installed a CUDA-13 build on a driver that only supports CUDA 12.9.** The pod's NVIDIA driver (550.127.05) caps out at CUDA 12.9, but plain `torch` (no pinned CUDA index) resolved to the latest release (2.13.0), whose default PyPI wheel had moved to CUDA 13. `torch.cuda.is_available()` doesn't raise on this mismatch — it just returns `False`, so the failure only surfaced as a downstream `AssertionError` in the smoke test, not a clear driver error. Fixed by pinning `torch==2.6.0`/`torchvision==0.21.0` via `--extra-index-url https://download.pytorch.org/whl/cu124` in `worker/requirements.txt` (cu124 is forward-compatible with any CUDA-12.x driver). Also discovered `QwenImageEditPlusPipeline` needs `torchvision` (for `Qwen2VLVideoProcessor`), which wasn't in the model card's minimal quickstart or `claude.md`'s tool list — added explicitly.
  2. **Worker → control-plane HTTP calls had no timeout**, so when the SSH reverse tunnel had a transient blip mid-request, `requests` hung indefinitely instead of raising — the process sat in a `CLOSE-WAIT` socket state with 0% CPU and no error, no retry, no progress, and no lease-expiry escape (the job was already marked `running`, past the point `lease_next`'s reclaim logic checks). Fixed by adding an explicit `timeout=` to every internal-API call in `worker/worker.py` (30s for control calls, 120s for the output PUT) — a stalled connection now raises promptly, gets caught by `run_forever`'s exception handler, and reports `/fail` for a clean retry instead of hanging forever.
- **M3 fully closed** (2026-08-19): live RunPod A100 80GB PCIe pod provisioned, `worker/setup.sh` + the two fixes above got `look_generation.py` running for real; `POST /profiles/{id}/looks` against the golden profile → 4 candidates generated (Qwen-Image-Edit-2511, seeds 0–3, 40 steps each, ~5min/candidate) → all 4 visually confirmed: mic on the correct side, black polo, tech home-office setting, strong identity match against the real reference photo. `POST /looks/{id}/approve` exercised for real. Pod terminated immediately after — total spend **~$2.15** of the $10 budget (balance $10.21 → $8.06). See `QA.md`'s M3 row for the full verification write-up.

## M4 — Claude orchestrator

- **`ORCHESTRATOR_MODEL=claude-sonnet-5` re-verified as current** (2026-08-19), per `claude.md`'s instruction to re-check at M4 build time — still the correct, current-generation Sonnet model ID. No change from the M0 scaffold decision.
- **`temperature` is not a valid parameter for `claude-sonnet-5`** — `claude.md` §7's "temperature ≤0.4" instruction is stale against the live API. A real call with `temperature` set returned `400 invalid_request_error: temperature is deprecated for this model` (current-generation Sonnet/Opus tiers have removed client-settable sampling params entirely). Per `claude.md` §2's "the README wins" rule, `orchestrator.py` omits `temperature` entirely rather than substituting another sampling knob.
- **Structured output via `client.messages.parse(output_format=OrchestratorOutput)`** (the SDK's recommended pattern, not raw `output_config` + manual `json.loads`) — this validates the response against the pydantic model automatically and returns `response.parsed_output`, already the typed object. `response.parsed_output` can be `None` (e.g. on a non-`end_turn` stop); `orchestrator.py` raises a `ValueError` in that case so it's caught by the same one-retry-then-fail path as a pydantic `ValidationError`.
- **`OrchestratorOutput` carries two mechanically-checkable validators** beyond basic field typing, both straight from claude.md §8's system-prompt rules: (1) `"".join(tts_chunks) == tagged_script` exactly (rule 5), and (2) every chunk ≤2500 chars (rule 5). A third check confirms `style_prompt` contains "talking" (rule 7). The "never change script words" and "sparse tagging" rules are semantic, not mechanically validatable — left to the system prompt and to the live-verification wording-diff check instead of a runtime validator (validating them at runtime would be fragile and could reject good output on edge cases like added ellipses).
- **`anthropic==0.122.0` added to `requirements.txt`** (latest at build time via `pip index versions anthropic`) — not previously a dependency.
- **M4 fully closed** (2026-08-19): 9 mocked unit tests (pydantic validators + `orchestrate()`'s retry-then-fail behavior, no live API calls) all pass. Live verification against the real Anthropic API using the actual golden-fixture `emotion_brief.txt`/`script.txt` (a genuine serious→warm→confident→calm arc): wording-diff check confirmed all 234 words identical between the original script and the tagged output (tags/punctuation only); 4 tags placed at points matching the brief's arc (`[warmly]` at the pivot line, `[smiling]` at self-intro, `[confident]` through the capabilities list, `[sincere]` at the close) — sparse, not over-tagged; `style_prompt` included "talking, speaking directly to camera" and zero appearance/clothing descriptors; both pydantic validators passed on the real output without needing a retry.

- **Six real bugs found and fixed via the live M5 pod run** (2026-08-19), none of which would have surfaced from reading the READMEs alone:
  1. **RunPod's `/workspace` is a network-mounted volume capped at whatever `volumeInGb` was set at pod creation (20GB, copied from M3's setting)** — separate from the pod's root overlay filesystem, which gets the full `containerDiskInGb` (150GB) with no extra quota. LiveAvatar's weights alone (46GB) blow past a 20GB volume. Fixed by installing LiveAvatar/SeedVR2 under `/root` instead of `/workspace` — `worker/setup.sh` and both handlers' `LIVEAVATAR_DIR`/`SEEDVR2_DIR` defaults now point there. Tradeoff: `/root` doesn't survive a pod restart the way a real persistent volume would; acceptable for this single-session test, revisit if a long-lived worker pod is ever kept running.
  2. **`deepspeed` (unpinned in LiveAvatar's `requirements.txt`, resolved to latest `0.19.5`) has a circular-import bug against the repo's own pinned `transformers<=4.51.3`** — `transformers.modeling_utils` imports `deepspeed`, which imports `transformers.models.opt.modeling_opt`, which needs `PreTrainedModel` from the still-initializing `modeling_utils` module. Fixed by downgrading to `deepspeed==0.15.4` (contemporaneous with that transformers pin).
  3. **`--fp8` requires Hopper-class native FP8 tensor cores** — fails on Ampere (A100) with `triton.compiler.errors.CompilationError: type fp8e4nv not supported in this architecture`. claude.md already flagged A100 as FP8-incapable; confirmed live and fixed `LIVEAVATAR_ENABLE_FP8`'s code default from `true` to `false` (matching `.env.example`, which already had it right).
  4. **`worker.py` eagerly imported all three handler modules at the top of the file**, which meant `look_generation.py`'s module-level `import torch`/`diffusers` was required just to *start* the worker process — even on a pod that only ever runs `video_generation`/`upscale` (which deliberately subprocess out to LiveAvatar/SeedVR2's own isolated venvs and don't need torch in-process at all). Fixed with lazy per-job `importlib.import_module()` lookups in the dispatch loop, so a handler's dependencies are only required when that job type actually runs.
  5. **Passing a custom `env` dict to `subprocess.Popen` silently drops whatever `PATH` the parent process happened to start with** — a bare `"torchrun"` command resolved to the pod image's unrelated system-wide PyTorch install (`/usr/local/bin/torchrun`, Python 3.12, no numpy/PIL) instead of LiveAvatar's own venv. Fixed by invoking the venv's `torchrun` by full path (`f"{LIVEAVATAR_DIR}/.venv/bin/torchrun"`) rather than relying on `PATH` resolution.
  6. **The audio/video duration-drift check compared the wrong duration.** `ffprobe -show_format`'s container-level `duration` follows the **longest** stream, not the video track — so muxing a video shorter than its audio (found live: a deliberately short `num_clip=1` test video against a longer test audio) produces a valid-looking file whose container duration matches the audio while the video track itself freezes/ends early, with no error. `_ffprobe_duration` now takes an explicit `stream` selector (`-select_streams v:0`) and the check runs **before** muxing, against the upscaled video's own duration vs. the audio's — catching a too-short video as a clear failure instead of silently shipping a broken mux. Re-verified independently via `ffprobe` on the actual output file after the fix (video 6.56s / audio 6.48s / 0.08s drift, well under the 0.2s limit) and by visually inspecting a frame at the very end of the video (real content, mouth mid-speech, no freeze).
- **M5 fully closed** (2026-08-19): live end-to-end run on the golden profile's real approved M3 look image + real ElevenLabs TTS audio (6.53s, `[confident]` tag) → `video_generation` (LiveAvatar, multi-clip, auto-covering the full audio) → `upscale` (SeedVR2, 2160p) → final mux. Visually verified: natural eye blinking, evolving mouth shapes tracking speech, natural hand gesture matching the style_prompt, identity/scene held consistent with the M3 approved look throughout — including at the very last frame. ## M6 — End-to-end wiring + frontend wizard

- **`POST /videos` is synchronous through orchestrate + TTS, then hands off to the job queue** — same precedent as M2's voice-clone endpoint: Claude orchestration and ElevenLabs synthesis are each single API calls that complete in a few seconds, so there's no benefit to routing them through the DB-backed job queue built for the GPU worker's long-poll pattern. The request blocks through `orchestrating` → `tts` status, writes the audio to S3, then enqueues `video_generation` (which auto-chains to `upscale` on completion via `domain_side_effects.py`) and returns immediately. `cost_ledger` accumulates `claude_input_tokens`/`claude_output_tokens` (from `orchestrate()`'s new `OrchestratorResult`, which now also returns `response.usage`) and `elevenlabs_chars`/`audio_duration_s` at each stage.
- **`domain_side_effects.py` extracted from `routes/internal.py`** as the single place that translates a generic job's completion/failure into domain-row updates (`Look`/`VideoRequest`) and auto-enqueues the next stage. Keeps the worker protocol (`/internal/jobs/*`) fully domain-agnostic per M3's original design, while giving the `video_generation → upscale` auto-chain and the `Look` candidate-key writeback one shared, testable seam instead of duplicating job-type branches inline in the route handler.
- **Reroll bug found and fixed**: `look_generation.py`'s worker handler used a fixed `SEEDS = [0, 1, 2, 3]` for every request, so the UI's "reroll" button (re-queueing the same look) produced byte-identical candidates every time — silently defeating claude.md §M3's stated reroll mitigation for inconsistent Qwen edits. Fixed by generating a fresh `random.sample` of seeds per `POST /profiles/{id}/looks` call in the route handler and passing them through the job payload (`worker/handlers/look_generation.py` now reads `payload.get("seeds")`, falling back to the old fixed list only if a payload omits it).
- **`LookOut` now returns presigned `candidate_urls`/`approved_url`, not raw S3 keys** — the frontend candidate grid and approved-look preview need browser-fetchable URLs; raw `s3_key` values aren't. Presigned at read time in `routes/looks.py`, matching the existing `presign_get` pattern from M3.
- **Two real bugs found via a live Playwright browser run against the actual dev server + API** (2026-08-19), neither caught by lint/typecheck/unit tests:
  1. **Hydration mismatch, self-inflicted by an earlier lint fix.** To silence `react-hooks/set-state-in-effect`, the wizard layout's and setup page's auth-gate state (`authorized`/`loggedIn`) had been moved into a lazy `useState(() => Boolean(getToken()) ...)` initializer. `getToken()` reads `localStorage`, which doesn't exist during SSR — so the initializer's server-side call always evaluates to `false`, while the *same* initializer function runs again on the client during hydration and sees the real (already-populated) `localStorage`, evaluating to `true`. Server-rendered HTML and the client's first hydration render therefore differed, and React threw a hydration-mismatch error on every direct navigation/reload of any wizard route. Fixed by reverting to the objectively-correct-for-SSR pattern: state defaults identically on server and client (`null`/`false`), and the real localStorage check moves into a `useEffect` (client-only, runs post-hydration) with a justified, narrowly-scoped `eslint-disable-next-line react-hooks/set-state-in-effect` — this is exactly the legitimate exception that lint rule allows for, not a style violation. `(wizard)/layout.tsx` additionally needed a tri-state `authorized: boolean | null` (not just `boolean`) so the redirect-on-unauthorized effect doesn't fire against the still-unknown default before the real check has run.
  2. **`/create`'s approval guard only checked for a stored `look_id`, not whether that look was actually approved.** `localStorage`'s `synctalk_look_id` is written as soon as a look is *generated* (`/looks` page, so the Create page can find its way back to the right look later), not when it's approved — so generating a look and then navigating straight to `/create` incorrectly let the Create form render instead of showing the "approve one first" message. Fixed by fetching the look via `api.getLook(lookId)` in a mount effect and gating on `look.approved_key` being set, with a `lookChecked` tri-state guard (mirrors the pattern in fix #1) so the check itself doesn't introduce a flash-of-wrong-content or a hydration mismatch of its own.
- **CI extended to cover `apps/web`** — M0's `ci.yml` only ever ran the backend gate (ruff/mypy/pytest); with a real frontend now existing, the `test` job was renamed `api` and a sibling `web` job added (`npm ci` → `eslint` → `next build`, Node 22). Both bugs found in this milestone's Playwright run would have shipped past `eslint`/`tsc` alone (they're runtime/hydration issues, not type errors) — CI catches the bugs *lint already covers* going forward; the browser-level check remains a manual/agent-driven step, not yet automated in CI.
- **Real bug in the first CI run itself**: an initial standalone `tsc --noEmit` step (in addition to `next build`) passed locally but failed on GitHub's runner with `Cannot find name 'LayoutProps'` in Next's own scaffolded `src/app/layout.tsx` — masked locally because this machine's `apps/web/.next/` directory (built earlier while testing the wizard) already had the ambient ".next/types/" declarations Next.js 16 generates as *part of* `next build`/`next dev`; a fresh checkout has no `.next/` yet, so a `tsc` run that isn't preceded by a Next build/dev pass fails on any file using Next's typed-route/layout helpers. Confirmed by reproducing locally against a clean `rm -rf .next` (fails) vs. `npm run build` alone (passes — it runs its own "Running TypeScript ..." pass after generating those types). Fixed by dropping the standalone `tsc` step; `next build`'s own TypeScript pass is the real, sufficient gate.

## M7 — Hardening

- **Idempotency keys scoped to the real-cost POSTs, not literally every POST** — claude.md says "idempotency keys on all POSTs"; applied to `POST /profiles/{id}/voice` (real ElevenLabs IVC), `POST /profiles/{id}/looks` (real GPU job), and `POST /videos` (real Claude + ElevenLabs + GPU cost, and the exact endpoint claude.md's M7 acceptance test names). Skipped on routes with no external cost where a duplicate is just a harmless extra DB row (`create_profile`, `create_asset`, `confirm_consent`, `approve_look`) or that are safe to retry by nature (presign). Generic `IdempotencyKey(key, endpoint)` table + `services/idempotency.py` (`get_cached`/`claim`/`store_result`/`release`) so any future route can adopt the same pattern. **`release()` matters**: a request that fails *after* `claim()` but before `store_result()` (a validation error, a downstream API failure) would otherwise leave the key permanently stuck — `get_cached` only recognizes a *resolved* row, so a genuine retry would just hit `claim()` again and get a false "already in progress" 409 forever. Every wired route wraps its post-claim work in `try/except Exception: release(); raise`.
- **Verified live against the real running stack, not just mocked**: duplicate `POST /profiles/{id}/looks` with the same `Idempotency-Key` returned byte-identical responses and left exactly one `Look`/`Job` row in the DB (confirmed via direct `psql` query). Duplicate `POST /videos` with the same key likewise returned identical responses with exactly one `VideoRequest`/`Job` row — critically, `cost_ledger` on the resulting row shows real orchestrate+TTS output (215 Claude output tokens, 43 ElevenLabs chars, 3.24s audio) that only happened **once**, confirming the second call was served entirely from cache rather than re-running (and re-billing) the real API calls.
- **Content moderation gate (`services/moderation.py`)**: a cheap `claude-sonnet-5` classification call (reusing `ORCHESTRATOR_MODEL`, `client.messages.parse` structured output, same pattern as M4's orchestrator) applied to look prompts (`POST /profiles/{id}/looks`) and both the emotion brief and script (`POST /videos`), per claude.md's "refuse look prompts and scripts that request a different real person than the profile owner." The real safety guarantee is architectural — every profile is bound to one consented owner and every generation only ever uses that owner's own reference assets, so there's no way to actually feed the pipeline someone else's likeness even if a prompt asked for one; this is defense-in-depth on top of that, not the primary control.
- **Moderation fails open on an API error or unparseable response** (logs a warning, lets the request through) rather than fails closed. Deliberate: the architectural consent-binding above is the real guarantee, and this is a single-owner-user tool — blocking the product's only user over a transient Anthropic API hiccup is worse than the narrow residual risk. Documented as a real trade-off, not an oversight.
- **Verified live**: a look prompt naming a real public figure ("make me look exactly like Tom Cruise from Top Gun") was correctly flagged and rejected with a 400 before any GPU job was queued; a video script impersonating a named real person ("Hi, I am actually Elon Musk speaking to you directly") was correctly flagged and rejected before any Claude orchestration or ElevenLabs TTS call fired (zero cost incurred on the rejected path). 4 mocked unit tests (`tests/test_moderation.py`, same pattern as M4's orchestrator tests) cover flagged/clean/API-error/unparseable-response branches without live API cost.
- **Structured JSON logging** (`app/logging_config.py` + `app/request_logging.py`): every log line, anywhere in the app, is one JSON object (timestamp, level, logger, message, plus whatever extra fields the call site attached) via a custom `JsonFormatter` on the root logger — including uvicorn's own startup/access logs, re-routed through the same handler so output is uniformly parseable. `request_id` (reused from an inbound `X-Request-ID` header, or a fresh UUID) is bound to a `contextvars.ContextVar` by `RequestLoggingMiddleware` and auto-attached to every log record emitted anywhere during that request's async task via a `logging.Filter` — services like `moderation.py` don't need `request_id` threaded through their function signatures for it to show up in their log lines. `job_id` is attached the ordinary way via `extra={...}` at the handful of call sites that have it (`services/jobs.py`'s enqueue/lease/complete/fail lifecycle events). The GPU worker (`worker/worker.py`, a separate process with no HTTP request of its own) gets a matching hand-rolled `log()` helper emitting the same JSON shape, keyed by `job_id` instead of `request_id`, replacing its previous plain `print()` calls.
- **Verified live**: sent `GET /metrics` with `X-Request-ID: test-req-123` and confirmed (a) the header was echoed back on the response, and (b) the container's log output contained a `{"logger": "app.request", "message": "request completed", "request_id": "test-req-123", ...}` line with method/path/status_code/duration_ms — end-to-end proof the contextvar propagation actually works, not just that the code compiles.
- **`/metrics` basic counters** (`GET /api/v1/metrics`, JWT-authenticated like every other non-`/internal` route): plain JSON counts — profiles/looks/video_requests totals, looks/video_requests by status, jobs by status and by type — via `GROUP BY` queries, not Prometheus exposition format. claude.md just says "basic counters" with no format mandated; JSON keeps it consistent with the rest of the API (every other endpoint is JSON) rather than adding a second response format and a `prometheus_client` dependency for a single-user tool with no Prometheus scraper in the picture. `profiles_ready` was considered and dropped from scope — the checklist's "ready" boolean is computed per-profile from its assets (see `routes/profiles.py`'s `_build_checklist`), not a persisted column, so a cheap `COUNT` can't produce it; adding that would mean either persisting a `ready` column (a real schema change beyond M7's scope) or iterating every profile in Python on every `/metrics` call.
- **S3 lifecycle rule — real deviation from claude.md's literal wording, documented rather than forced to fit.** claude.md says "S3 lifecycle rule deletes raw uploads' temp copies after 7 days," but this build has no separate temp-copy concept: presigned uploads land directly at their permanent key (M1's design), and a *passed*-validation raw asset (photo/video/voice) is referenced indefinitely — `primary_ref_image_key` and profile photos are read again at every future look-generation call, not just within some initial window. A blanket 7-day expiry on all raw uploads would silently break look generation weeks after a profile was created. The genuinely disposable case is a raw upload that **failed** validation: `create_asset` (`routes/profiles.py`) now tags it (`services/storage.tag_for_expiry`, S3 object tagging) with `lifecycle=expire-failed-validation`, and `ensure_lifecycle_policy()` (called at API startup, alongside the existing `ensure_bucket_exists()`) registers a real, tag-filtered MinIO/S3 Lifecycle rule expiring anything carrying that tag after 7 days — verified live via `mc ilm rule list` (rule registered, correct tag/day count) and `mc tag list` on an actual failed-validation object uploaded through the real API (tag present). This is a real S3/MinIO bucket-level TTL mechanism, not an app-level cron job standing in for one.
- **Job lease-reclaim (already built in M3) verified against its literal M7 acceptance test**, not just assumed still correct: `tests/test_jobs.py` (real Postgres session, not mocked — `SELECT ... FOR UPDATE SKIP LOCKED` and unique-constraint semantics need real SQL) simulates a worker crashing mid-render (backdating `lease_expires_at` into the past) and confirms the exact same job gets reclaimed by a "second worker" and completes — literally claude.md's "kill the worker mid-render → job is reclaimed and retried once → completes." A second test confirms the bound: a job whose *reclaimed* lease also expires exceeds `MAX_ATTEMPTS` (2) and is marked permanently `failed` rather than reclaimed a third time, so a truly poisoned job doesn't retry forever.
